تسجيل الدخول (مرحلتان)
↑ العودة للفهرس
POST
/api/rest/v2/auth/login
تسجيل الدخول (مرحلتان) تسجيل دخول على مرحلتين عبر نفس الرابط. المرحلة الأولى: أرسل user_name و user_pass فقط (بدون pin_code) — يرد النظام بالكود 1002 (OTP sent) ويرسل رمز تحقق برسالة SMS إلى جوال الحساب، صالحًا لمدة expires_in ثانية. المرحلة الثانية: أعد نفس الطلب بنفس البيانات مع إضافة pin_code المستلم — يرد النظام بالكود 1001 مع data.api_token الذي تستخدمه بعدها في كل الطلبات المحمية عبر الهيدر "Authorization: Bearer <api_token>". إذا كان هناك توكن سابق تتم إعادة استخدامه (data.reused=true) إلا إذا أرسلت force_new_token=true.
التوثيق: لا يتطلب توكن
الحد (Rate limit): 10/min
Headers
الاسم	إلزامي	مثال
Content-Type	نعم	application/json
Body
الاسم	النوع	إلزامي	الشرح
user_name	string	نعم	اسم المستخدم
user_pass	string	نعم	كلمة المرور
pin_code	string	لا	رمز OTP (4 أو 6 أرقام) يصلك برسالة SMS بعد المرحلة الأولى. لا تُرسله في المرحلة الأولى؛ مطلوب في المرحلة الثانية.
force_new_token	boolean	لا	قيمة منطقية اختيارية. عند true يتم إصدار api_token جديد دائمًا بدل إعادة استخدام التوكن الحالي.
مثال cURL
# Step 1: send credentials WITHOUT pin_code -> an OTP is sent to the account mobile
curl -X POST "https://hotsms.ps/api/rest/v2/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"user_name":"demo","user_pass":"demo"}'

# Response: {"status":true,"code":1002,"message":"OTP sent","data":{"otp_required":true,"expires_in":120}}

# Step 2: repeat the SAME request WITH the pin_code received by SMS -> returns api_token
curl -X POST "https://hotsms.ps/api/rest/v2/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"user_name":"demo","user_pass":"demo","pin_code":"123456"}'
مثال نجاح
{
    "step_1_response": {
        "status": true,
        "code": 1002,
        "message": "OTP sent",
        "data": {
            "otp_required": true,
            "expires_in": 120
        }
    },
    "step_2_response": {
        "status": true,
        "code": 1001,
        "message": "Success",
        "data": {
            "api_token": "<60-char token used as Authorization: Bearer>",
            "reused": false
        }
    }
}

Headers

X-API-TOKEN	لا	<api_token>
Content-Type	نعم	application/json
Body

الاستعلام عن حالة اسم مرسل
↑ العودة للفهرس
GET
/api/rest/v2/senders/status
الاستعلام عن حالة اسم مرسل أرسل sender_name ضمن معاملات رابط GET (نص مطلوب، بحد أقصى 50 حرفاً لدعم الأسماء القديمة). يرجع أحدث طلب مطابق ضمن الحساب مباشرة في data بنفس حقول قائمة الطلبات. المطابقة للاسم الكامل مع تجاهل حالة الأحرف والمسافات على الأطراف، دون بحث جزئي أو رموز بديلة. يتم اختيار الأحدث حسب send_date ثم send_time ثم send_no. الحالات: 0=pending، 1=approved، 2=rejected، 3=deleted، 4=blocked، وأي قيمة أخرى unknown. إذا لم يوجد طلب مطابق يرجع HTTP 404 والكود 1004 ورسالة Sender request not found؛ ويشمل ذلك الأسماء التابعة لحساب آخر أو الموجودة فقط في قائمة أسماء الحساب دون طلب تسجيل. المدخلات غير الصحيحة ترجع HTTP 422. متاح فقط على REST v2 باستخدام api_token.
التوثيق: يتطلب توكن
Headers
الاسم	إلزامي	مثال
Authorization	نعم	Bearer <api_token>
Accept	نعم	application/json
مثال cURL
curl -G "https://hotsms.ps/api/rest/v2/senders/status" \
  -H "Authorization: Bearer <api_token>" \
  -H "Accept: application/json" \
  --data-urlencode "sender_name=MyBrand"
مثال نجاح
{
    "status": true,
    "code": 1001,
    "message": "Success",
    "data": {
        "send_no": 18451,
        "sender_name": "MyBrand",
        "authorized_name": "Ahmed Ali",
        "company_name": "Example Co",
        "mobile": "970599999999",
        "notes": "Marketing SMS",
        "user_name": "demo",
        "user_name_activate": "",
        "send_date": "2026-08-30",
        "send_time": "21:10:05",
        "send_ok": 0,
        "send_auth": 0,
        "status": "pending",
        "has_attachment": false,
        "attachment": null
    }
}
جميع القيم الممكنة لحالة اسم المرسل (enum)
الحقل data.send_ok هو حالة طلب التسجيل كرقم صحيح، والحقل data.status هو الاسم النصّي الثابت المقابل لها. الجدول يعرض جميع القيم النصّية الممكنة. أما status خارج data فهو قيمة منطقية تدل على نجاح الاستعلام، ولا يدل على اعتماد اسم المرسل.

data.send_ok (integer)	data.status (string enum)	الشرح
0	pending	طلب التسجيل قيد المراجعة أو بانتظار الموافقة.
1	approved	طلب التسجيل معتمد.
2	rejected	طلب التسجيل مرفوض.
3	deleted	تسجيل اسم المرسل محذوف.
4	blocked	اسم المرسل محظور.
أي رقم صحيح آخر	unknown	قيمة رقمية غير معروفة؛ تعامل معها كحالة غير معروفة وليست معتمدة.
مثال: data.send_ok=0 يقابله دائماً data.status="pending". إرجاع HTTP 200 وstatus=true خارج data يعني نجاح الاستعلام، حتى لو كان الطلب قيد المراجعة أو مرفوضاً أو محذوفاً أو محظوراً. عدم وجود طلب مطابق يرجع HTTP 404، ولا يرجع حالة unknown.

إضافة اسم مرسل
↑ العودة للفهرس
POST
/api/rest/v2/senders
إضافة اسم مرسل تسجيل اسم مرسل بحالة send_ok=0 (بانتظار التفعيل)، بنفس قواعد صفحة المشترك. التفويض اختياري: يمكن إضافته لاحقاً عبر data.send_no، أو إرفاق ملف PDF/JPG/PNG (حتى 10MB) في نفس الطلب. يُحفظ الملف في مجلد auth_letter الخاص بالبورتال باسم {send_no}.{ext}.
التوثيق: يتطلب توكن
الحد (Rate limit): 30/min
Headers
الاسم	إلزامي	مثال
Authorization	نعم	Bearer <api_token>
Content-Type	نعم	multipart/form-data
Body
الاسم	النوع	إلزامي	الشرح
sender_name	string	نعم	من 1 إلى 11 حرفاً، ويجب أن يحتوي حرفاً إنجليزياً. المسموح: حروف وأرقام إنجليزية ومسافة ونقطة (.) وشرطة سفلية (_) وشرطة (-).
authorized_name	string	نعم	اسم الشخص المفوض باستخدام اسم المرسل.
company_name	string	نعم	اسم الشركة أو المؤسسة.
mobile	string	نعم	رقم الجوال للتواصل (صيغة محلية أو دولية).
notes	string	لا	ملاحظة اختيارية عن طبيعة الاستخدام (حد أقصى 500).
attachment	file	لا	ملف التفويض اختياري: PDF أو JPG/PNG حتى 10MB.
مثال cURL
# Add the name only, then upload the letter later using data.send_no
curl -X POST "https://hotsms.ps/api/rest/v2/senders" \
  -H "Authorization: Bearer <api_token>" \
  -F "sender_name=MyBrand" \
  -F "authorized_name=Ahmed Ali" \
  -F "company_name=Example Co" \
  -F "mobile=970599999999" \
  -F "notes=Marketing SMS"

# Or add the name and the authorization letter together
curl -X POST "https://hotsms.ps/api/rest/v2/senders" \
  -H "Authorization: Bearer <api_token>" \
  -F "sender_name=MyBrand" \
  -F "authorized_name=Ahmed Ali" \
  -F "company_name=Example Co" \
  -F "mobile=970599999999" \
  -F "notes=Marketing SMS" \
  -F "attachment=@letter.pdf"
مثال نجاح
{
    "status": true,
    "code": 1001,
    "message": "Success",
    "data": {
        "send_no": 18451,
        "sender_name": "MyBrand",
        "send_ok": 0,
        "send_auth": 0,
        "status": "pending",
        "message": "Sender name added. Upload the authorization letter using send_no.",
        "has_attachment": false,
        "attachment": null
    }
}

رفع التفويض
↑ العودة للفهرس
POST
/api/rest/v2/senders/{send_no}/authorization
رفع التفويض رفع أو استبدال ملف التفويض لاسم مرسل يملكه الحساب. الرقم send_no يأتي من رد الإضافة أو من قائمة الطلبات. الاسم غير المفعّل يمكن استبدال ملفه؛ الاسم قيد التفعيل يُرفع له التفويض فقط إن لم يكن هناك ملف.
التوثيق: يتطلب توكن

إرسال رسالة إرسال رسالة SMS إلى رقم واحد أو عدة أرقام. تُخصم كلفة الإرسال من رصيد الحساب، ويعرض الرد ملخصًا يشمل عدد الأرقام المقبولة والمرفوضة وتقرير الشبكات والكلفة الإجمالية وأرقامًا مرجعية للرسائل يمكنك متابعتها لاحقًا. يجب أن يكون اسم المرسل من الأسماء المعتمدة في حسابك.

Content-Type	نعم	بحسب طريقة إرسال البيانات المختارة؛ راجع الأمثلة أدناه.

Body

طرق إرسال البيانات
يدعم مسار إرسال الرسائل هذا الحقول نفسها mobile وmessage وsender بالطرق الثلاث. اختر طريقة واحدة لكل طلب. تُذكر متطلبات المسارات الأخرى في توثيق كل مسار.

الطريقة	الاختيار في Postman Body	Content-Type
JSON — موصى به	raw → JSON	application/json
Form Data	form-data	multipart/form-data; boundary=...
URL Encoded	x-www-form-urlencoded	application/x-www-form-urlencoded
يحدد Content-Type صيغة البيانات التي ترسلها، بينما يطلب Accept: application/json ردًا بصيغة JSON. استخدم Bearer Token نفسه مع جميع الطرق.

عند استخدام Form Data، يولّد Postman وPHP cURL الهيدر multipart/form-data والـ boundary تلقائيًا. يفصل boundary بين الحقول. احذف أي Content-Type أضفته يدويًا عند الانتقال إلى Form Data.

في Postman اختر raw → JSON بدل Text. قيمة Content-Type المضافة يدويًا تتجاوز القيمة التلقائية.

يحتوي مجلد Messages على ثلاثة أمثلة محفوظة: Send message — JSON وSend message — Form Data وSend message — URL Encoded. كلها تستخدم المسار نفسه. شغّل مثالًا واحدًا؛ تشغيل الثلاثة يرسل ثلاث رسائل.

تحديث حالة رسالة واتساب أرشيفية
↑ العودة للفهرس

/api/rest/v2/messages/archive/status
تحديث حالة رسالة واتساب أرشيفية يحدّث التقرير الحالي لنفس sms_ref وmobile معًا في رسالة واتساب أرشيفية تخص الحساب المحدد بالتوكن. تُكتب الحالة الجديدة فوق تقرير هذا الرقم ضمن هذا المرجع فقط، دون تجميع الحالات. مثلًا: تحديث الرقم 972599999999 ضمن المرجع 501 يبقي تقريره ضمن المرجع 502 وتقارير بقية مستلمي المرجع 501 كما هي. يجب أن يكون sms_type المحفوظ في قاعدة البيانات 300، ولا يلزم إرساله في طلب التحديث. النوعان 1 و2 يبقيان على نظام تقارير SMS المعتاد، ولا يمكن تحديثهما هنا. الحالات المقبولة حرفيًا: Accpted وSent وDelivered وRead وFailed. لا يُخصم رصيد ولا تُرسل رسالة. تُطبّق الطلبات حسب ترتيب معالجتها، وتكرار الحالة نفسها يحافظ على وقتها. updated_at هو وقت الحالة على الخادم، ويظهر أيضًا في حقل delivered_at بتقارير السجل؛ يبقى تاريخ ووقت الرسالة الأصلي كما هو. يرجع HTTP 404 والكود 1604 عند غياب الرسالة أو اختلاف المالك أو النوع أو عدم وجود الرقم ضمن مستلميها، وHTTP 422 للمدخلات غير الصالحة. status في أعلى الرد يعني نجاح الطلب، وdata.status هي حالة الرسالة.
